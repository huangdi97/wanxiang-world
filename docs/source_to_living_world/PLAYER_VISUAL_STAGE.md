# Player Visual Stage — Source -> Visual Living World

## 1. Product contract

The Experience Player is a **visual projection over one authoritative living world**.
It is not a second runtime, a second truth store, or a handcrafted scene editor.

For a book/source-driven world the product path is:

```text
Source
  -> semantic candidates + evidence + rights
  -> WorldDraft / WorldPackageDraft
  -> source-grounded visual plan
  -> T0 or T1 visual asset projection
  -> Playable profile
  -> Living World Stage
  -> player command
  -> Commit Authority
  -> committed state projection
  -> refreshed Stage
```

A visual asset can make a world easier to inhabit, but it never becomes Canonical
World State merely because it looks plausible.

## 2. Cost model

### T0 — deterministic zero-cost projection

T0 is always available for an eligible source-grounded place:

- deterministic procedural SVG;
- no image API;
- no external network;
- no manual per-book scene template;
- cache key pinned to source/style/provider identity;
- safe fallback for private sources.

T0 exists so **every valid source can produce actual pixels**, not a text-only
placeholder.

### T1 — optional external image provider

T1 is a replaceable provider behind the same bounded scene request:

- explicit network opt-in;
- explicit source-rights permission for external processing;
- explicit cost-unit budget;
- provider id/version in the cache key;
- generated bytes are content-addressed;
- private sources require a private-safe provider;
- the provider receives a bounded scene brief, not the raw book by default;
- outgoing briefs enforce finite place/context/reference lengths and item counts, including for hostile or unexpectedly long metadata.

The Authoring and Player surfaces share the same visual cache. A T1 asset created
during authoring must survive Playable registration as the same T1 asset; Player
must not silently regenerate a T0 SVG.

## 3. Grounding rules

Visual generation may use:

- source-derived place names;
- source references;
- bounded source-grounded context candidates;
- deterministic story-style identity.

It must not invent authoritative:

- geographic coordinates;
- character-to-place placement when the draft has no such evidence;
- routes or adjacency that were not extracted from the source;
- world events, relationships, or rules merely to enrich an image.

The narrative atlas follows the same rule: nodes are source places; edges exist
only for source-grounded topology relations. Atlas coordinates are layout
coordinates, not geography.

## 4. Living World Stage

The Player view is **stage-first**, not dashboard-first.

### Layer A — world image

The scene image occupies the primary viewport. T0 SVG and T1 raster images use
the same projection contract. A subtle pointer parallax is presentation-only and
is disabled by reduced-motion preference.

### Layer B — world HUD

Time, place, environment, weather, mode, and world identity are projected over
the scene. They are read models from server truth, not browser-owned state.

### Layer C — live narrative

Current narrative, current event, present people, opportunities, and
source-grounding clues sit on top of the world as contextual overlays. They do
not write anything by themselves.

### Layer D — action dock

The action input and suggested actions are the primary control surface. An action
is still accepted only through the existing Player command route and Commit
Authority. Observer mode keeps the dock disabled.

Character state, committed changes, chronicle, memories, inventory, goals, and
relationships live below the stage as a world record, not as competing primary
panels.

## 5. Mobile behavior

Mobile is not a desktop grid collapsed to one column.

- the stage remains the dominant surface;
- HUD becomes a compact two-column overlay;
- narrative and context occupy dedicated vertical stage bands;
- the action dock stays reachable near the viewport bottom;
- world record panels stack below the stage;
- no hover-only interaction is required.

## 6. Rights and privacy

Visual delivery is separately gated from world/profile visibility.

- owner access may view source-gated visuals;
- public viewers receive only assets whose delivery rights are public;
- on-demand place generation first checks world access and visual access;
- external generation also checks external-processing permission and cost budget;
- blob storage and cache metadata remain outside Canonical World State.

## 7. Architecture boundaries

The Stage may change presentation without changing world semantics.

It must not:

- create a second event/history/branch/state system;
- bypass Commit Authority;
- treat image-provider success as world truth;
- store canonical mutations in browser state;
- special-case one book/world in Core;
- claim external 3D/GPU/model capabilities without runtime evidence.

Actual Godot/3D engine integration remains an external capability gate. The
current Stage intentionally delivers a low-cost immersive 2D/2.5D experience
without requiring every source to become a hand-built 3D production.

## 8. Acceptance

Automated acceptance must prove at minimum:

1. source -> visual plan -> cached visual asset;
2. T1 provider governance and cache reuse;
3. Authoring -> Playable handoff does not downgrade T1 to T0;
4. Player world detail exposes atlas/scenes/places under rights gates;
5. entering observer/character mode shows the visual Stage;
6. Stage image occupies the dominant desktop viewport;
7. observer mode cannot submit a world action;
8. character action flows through the real command path and returns committed
   changes;
9. continue-session returns to the same authoritative world;
10. human visual acceptance remains a human gate and is never fabricated.

## Atlas as an actionable entrance

The book-derived Atlas is narrative topology, not geographic coordinates. In Player, its cover offers seven or fewer source-grounded place entrances: ready places select their cached scene; deferred places use the governed on-demand generation path. The full searchable place index remains below. Repeated clicks in the same browser session cannot start simultaneous duplicate scene generation requests. This is not proof of server-level concurrency coalescing or human visual acceptance.

### External client data minimization

The internal scene plan preserves source refs and evidence for audit. The network-facing T1 image client receives a brief without source locator references (no filenames/paragraph locators); it still receives the bounded place/context needed for consented image generation. External T1 content is restricted to PNG/JPEG/WebP; untrusted SVG and arbitrary image subtypes are rejected. These restrictions are not substitutes for source rights, authentication, or validation of image decoder safety.

### Scene-generation concurrency and local process coordination

The shared `VisualAssetCache` coordinates concurrent same-key requests within one cache instance. For `LocalJsonVisualCacheIndex`, an additional advisory lock file guards the full lookup → generate → blob store → index update sequence across cache instances **and OS processes sharing the same filesystem**. The cache is always re-read after the lock, so a second worker can reuse the first worker's asset instead of paying for a duplicate generation. This deliberately serializes the small local JSON cache across keys; the in-memory cache retains per-key concurrency.

This is a **single shared-filesystem** strategy, not an HA distributed lease. Independent hosts with separate cache volumes, a provider call that succeeds before a worker crash, cross-host cost accounting, and remote production object stores still require transactional shared cache/leases and provider idempotency or billing reconciliation. POSIX process behavior has a dedicated subprocess regression; Windows uses an OS byte-range lock and requires Windows runtime qualification. Do not declare distributed cost or billing gates passed on this evidence alone.

## Player scene-focus presentation mode (October 2026)

The Player includes an explicitly reversible **Focus on scene / 专注场景** control.
It temporarily hides HUD, narration and context overlays inside the visual
stage while preserving the stage image and the separate action dock. Mobile
uses a shorter scene height for a clearer first viewport. This is a UI-only
projection state: changing focus does not create an action, edit a location,
change an owner, or append canonical history. Browser E2E verifies both
normal and scene-focused views. A more visually immersive T1/T2/T3 renderer
still needs a real authorized provider and human review; this control must not
be reported as provider fidelity validation.

The personal relation panel reads the actor-scoped relation projection, not
the world's global relation graph. Known people may be listed as knowledge,
but only explicitly co-located people can be labeled present.
## T1 HTTP gateway and product fallback boundary (October 2026)

The deployable T1 HTTP adapter is intentionally narrower than a generic URL
fetcher:

- the endpoint comes from trusted deployment configuration or explicit
  composition-root injection, never from a Player/Studio request payload;
- remote HTTP is rejected; HTTPS is required except for loopback HTTP used by a
  local model gateway;
- literal link-local/private/reserved HTTPS targets are rejected by default;
- redirects are not followed, so an Authorization header is not forwarded to a
  second host;
- credentials/fragments in the endpoint and line breaks in bearer tokens are
  rejected;
- JSON response bytes are bounded before parsing, base64 is validated, and T1
  output must be PNG/JPEG/WebP with matching raster signatures;
- source locators and the full source are removed before the external client
  receives a scene brief.

This transport hardening does not make the configured provider authoritative.
Network egress/DNS policy, provider account security, real image-decoder
sandboxing, billing reconciliation and provider-specific retention terms remain
deployment responsibilities.

Product surfaces use a **T0-preserving tier selector** around the strict
materializer. A configured T1 provider is skipped, rather than breaking the
world preview, when any of these apply:

1. network use was not explicitly enabled;
2. source rights do not allow external model processing;
3. a private source is paired with a provider not declared private-safe;
4. the requested scene batch would exceed the declared visual cost budget.

Invalid provider definitions (for example negative cost) still fail loudly.
Direct low-level materializer calls also remain strict so tests and backend
integrations cannot mistake a policy violation for successful T1 execution.

Player visual proof exposes only safe generation provenance:
`provider_id@provider_version`, source-evidence count and the
projection-only warning. It does **not** expose source locators, prompts,
credentials, branch IDs, event IDs or canonical state hashes.

### T3 hot-swap identity

Verified spatial attachments expose an opaque, derived `asset_revision` token to
the Player projection. It is computed from the ordered verified AssetRefs but
does not expose object ids or raw content hashes. The browser spatial bridge
includes this token in its renderer sync identity, so replacing a T3 asset with
another asset of the same place, media type, count and projection frame still
forces an active renderer to unmount and reload. This is presentation cache
invalidation only; it is not Canon, source provenance, or a worldline revision.
